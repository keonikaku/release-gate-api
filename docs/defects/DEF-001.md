# DEF-001

**Issue type:** Bug
**Summary:** Every write to the API returns 500 because the service opens its database in a directory that does not exist
**Priority:** P1 Blocker
**Severity:** S1 Critical
**Reproducibility:** Always
**Status:** Closed
**Resolution:** Fixed
**Components:** API, Persistence
**Labels:** api, wiring, escaped-the-suite, deliberate
**Affects commit:** 383565e
**Found on run:** 30518441807
**Fix commit:** 2e3dce5
**Regression commit:** 5f05880
**Fix pull request:** 5
**Introduced by pull request:** 4
**Regression test:** tests/integration/test_change_api.py::test_the_real_store_wiring_opens_a_usable_database
**Existing case that should have caught it:** none existed
**Environment tested:** ubuntu-latest runner, Python 3.13, service built from the merge commit and served by uvicorn on 127.0.0.1:8000, SQLite on the runner's temporary directory

## Endpoints and consumers impacted

Every endpoint that touches stored state, which is four of the five the service
publishes:

| Endpoint | Effect |
|---|---|
| `POST /changes` | 500. No change can be created. |
| `GET /changes/{change_id}` | 500. No change can be read. |
| `POST /changes/{change_id}/submit` | 500. No change can be submitted for a gate decision. |
| `POST /changes/{change_id}/transition` | 500. No change can move through its lifecycle. |
| `GET /healthz` | Unaffected. Returns 200, which is the reason this got as far as it did. |

Any consumer of this API is fully blocked. There is no partial degradation and no
workaround: the service accepts connections, answers its health check, and fails
every request that does real work.

## Errant behaviour

A well formed request that should create a change returns HTTP 500 with a plain
text body of `Internal Server Error` and no JSON at all. The service logs
`sqlite3.OperationalError: unable to open database file`.

The 500 body is not the machine readable error envelope every other failure path
on this API returns. A consumer parsing the response as JSON gets a decode error
on top of the failure, so the caller cannot tell from the response what went
wrong.

## Expected behaviour

`POST /changes` with a valid submission returns 201 and the created change
record, including its identifier and its state of `draft`. The database is opened
at the path the deployment configures, and the service writes there.

## Steps to reproduce

1. Deploy the service at commit `383565e` on a host where `/var/lib/release-gate`
   does not exist, which is every host in this project.
2. Set `RELEASE_GATE_DB` to a writable path, for example `$RUNNER_TEMP/verify.db`.
   The bug ignores it, and that is part of the defect.
3. Start the service: `python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`.
4. Confirm the service is up: `GET /healthz` returns 200. This step matters,
   because a health check alone would report the service as healthy.
5. `POST /changes` with any valid submission body.
6. Observe 500 and a plain text body rather than 201 and a change record.

## Root cause

A configurable data directory was added, defaulting to `/var/lib/release-gate`.
Two things were wrong with it. The default names a directory that does not exist
on the machine the service runs on, and SQLite does not create missing parent
directories. And the configured database path was reduced to its file name and
appended to that directory, so `RELEASE_GATE_DB` no longer decided where the file
went. A deployment that set the documented environment variable was still sent to
the missing directory.

## Coverage gap analysis

**No existing test case should have caught this, because no case covered the code
path at all.** That is the finding, and it is more useful than the bug.

The whole suite passed on the commit that carried this defect. Every case that
touches the API injects its own database through the dependency override that
exists to keep tests isolated. `get_store`, the function that opens the real
database, was therefore executed by nothing in the suite. The tests were not weak
about this path. They did not have one.

Three consequences worth stating:

1. **Test isolation and production wiring pull in opposite directions.** The
   override that makes the suite fast and deterministic is exactly what hid this.
   That is not an argument against the override. It is an argument for having at
   least one case that does not use it.
2. **A health check is not a smoke test.** `GET /healthz` passed throughout,
   because it touches no storage. Any monitor watching only that endpoint would
   have reported the service healthy while every write failed.
3. **Unit testing the store would not have helped.** `Store` was never broken.
   The defect lived in the wiring between configuration and the store, which does
   not exist until the application is assembled and asked for one.

## Detection

Caught by the post-merge pipeline, at the step that builds a fresh instance,
serves it over HTTP and drives it as a client would. It was not caught by the
201 passing tests, and it would not have been caught by a pre-merge gate that
only runs the suite.

The pipeline held the release: promotion did not run, no version was tagged, and
production stayed on the previously promoted version.

## Resolution

The data directory default was removed and the configured path is honoured again.
The regression test was written and committed **before** the fix, so the history
carries a red commit followed by a green one in that order rather than a single
commit asserting both.

The regression test is the only case in the suite that assembles the application
without the store override, which is the gap this defect exposed.

## Note on this record

This defect was introduced deliberately, on a branch, to exercise the release
process end to end, and it was reverted immediately afterwards. It is labelled as
deliberate in its own commit message. Everything else about it is real: the run,
the failure, the block, the coverage gap and the fix are all as recorded.
